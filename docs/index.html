About and methodology

Read this first. PkgWatch lists packages as suspicious. It does not claim that any package is harmful. Everything here comes from automated pattern matching on source code that was never run, and false positives happen: build tools, security scanners and installers legitimately do many of the things an attack does. Treat every entry as a lead to check yourself. If a listing is wrong, use its “Report a false positive” link.

What it does

Every 20 minutes a GitHub Actions job reads what was newly published on npm and PyPI, downloads each package's metadata and archive into memory, and inspects them statically. Packages are never installed, imported or executed, and nothing is unpacked to disk. Packages that score 15 or more are listed here, in the JSON data files and in the RSS feeds. There are no servers, databases or paid services behind this page.

Scoring

Each detector that fires adds a weight. A package's risk score is the sum of the weights, capped at 100.

ScoreLevelMeaning
70–100highSeveral strong indicators together. A triage issue is opened for a human to review.
40–69mediumOne strong indicator, or a few weaker ones that reinforce each other.
15–39lowA single weak indicator. Usually benign; shown for completeness.
0–14not listedOnly counted in the aggregate statistics.

Detectors

Name

typosquat
The name is one or two edits (insert, delete, substitute, swap) from a popular package. Names of five characters or fewer only match at one edit.
name-manipulation
A popular name with separators changed, look-alike characters (rn for m, 1 for l, 0 for o), an added prefix or suffix such as python- or -utils, or npm scope confusion such as types-node for @types/node.
combosquat
A popular name joined to generic words, such as lodash-helper.
dependency-confusion
An internal-looking name (-internal, -private, -corp) first published at a very high version such as 99.0.0, or any first release with such a version.

Metadata

new-publisher-similar-name
A recently created package from a publisher with little history whose name resembles a popular package.
sparse-metadata
Missing or placeholder description, README or repository link. Never enough to list a package by itself.
repo-impersonation
The repository link points at the repository of the popular package being imitated.
popular-package-change
On a package that is itself popular: a newly added maintainer, or a large jump in size or version compared with the previous release.

Content

npm-install-hook
A preinstall, install or postinstall script. Routine native-build hooks are ignored; scripts that run a shell, a downloader or a bundled file score higher.
python-install-code
setup.py code (read as a syntax tree, never run) that opens network connections, starts processes, executes dynamic or decoded code, or writes outside the build directory; custom install commands; and .pth files with executable lines.
obfuscation
Code that decodes a hidden payload and executes it, long high-entropy strings, large base64 or hex blobs, character-code chains, and minified code in an otherwise tiny package.
exfiltration
Code that reads credential, browser, chat-token or wallet files, or serialises the whole environment, in a file that also makes network calls.
suspicious-endpoint
Hardcoded chat webhooks, tunnelling and request-capture hosts, paste sites, or URLs that use a raw IP address.
binary-dropper
Compiled executables in a package that is not declared as native, or code that downloads a file and then runs it.
unsafe-archive
The archive contains absolute paths or parent-directory entries and was not unpacked.

Limits

  • Static analysis only: behaviour that depends on runtime conditions, or that is hidden well enough, is missed.
  • Archives above 10 MB compressed or 50 MB unpacked are scored on name and metadata alone.
  • Publisher age is estimated; registries do not publish account creation dates.
  • A clean bill here means nothing: unlisted packages were not vetted, only not flagged.

Data and feeds

  • data/latest.json: the most recent 500 findings
  • data/stats.json: counts and trends
  • data/findings/index.json: the days available under data/findings/YYYY/MM/DD.json (kept for 365 days)
  • feed.xml and feed-high.xml: RSS 2.0
